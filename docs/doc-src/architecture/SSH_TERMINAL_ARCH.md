# SSH 终端接入设计报告

把终端执行面从「本地伪 Linux 环境」搬到「远端 SSH 主机」，难点不在连上 SSH，而在四个容易被忽略的契约：会话就绪信号、窗口尺寸下发、主机密钥校验和凭据落盘。任何一处漏掉，症状都会伪装成别的问题——命令明明执行成功却报超时、全屏程序画错行、连不上却被当成网络故障。

本报告给出可以直接照搬的分层、接口、不变量与验收清单，并标注每一步的真实失败表现，便于移植时快速判断自己漏了哪一环。

## 一、什么时候适用

适合：

- 应用内已经有一个终端视图与命令执行器，执行目标是本机内的沙箱 Linux（proot、chroot、Termux、busybox 之类）
- 希望把重负载执行挪到真正的 Linux 主机，同时保留设备侧文件浏览、存储挂载等能力
- 需要一个「可见会话」给用户敲命令，同时需要一个「不可见通道」给 Agent 或工具批量执行

不适合：

- 只需要一次性远程命令、不需要交互式 PTY、不需要窗口尺寸与全屏程序
- 目标是 SFTP 文件传输而非终端会话

## 二、核心设计取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 会话承载 | 直接使用 SSH `shell` 通道 + PTY | 不再经过本地沙箱，节省一层 ptrace 与一次环境安装 |
| 本地沙箱 | 保留但降级为可选目标 | 已发布行为不消失，用户显式选择才使用 |
| SSH 客户端 | JSch 的维护分支（`com.github.mwiede:jsch`） | 纯 Java，Android 与 JVM 通用；原版 `0.1.55` 无法与 OpenSSH 8.8+ 握手，因为对方默认关闭 `ssh-rsa` |
| 主机密钥 | 强制校验，首次使用 TOFU | `StrictHostKeyChecking=no` 等于放弃中间人防护 |
| 凭据存储 | 平台密钥库加密后再落盘 | 配置文件常被备份、导出、贴进 issue |
| 连接失败 | 直接报错并要求用户改配置 | 静默回落本地会让用户以为连的是远端，实际在本地跑 |

不做的事同样要写清楚：不引入自动降级，不做「连不上就用本地」的兜底，不在本地沙箱里再套一层 ssh 客户端。

## 三、分层与职责

```
terminal/
├── data/            会话、配置、目标枚举等纯数据
├── transport/       与提供者无关的会话传输抽象 + 本地/SSH 实现
├── provider/        会话提供者：按目标类型启动与关闭会话，隐藏执行、文件系统
├── utils/           连接管理、主机密钥库、凭据库、内嵌 sshd
├── view/            终端状态机与输出处理
└── ui/              终端界面、设置页、首次配置引导
```

各层职责与必须实现的关键点：

- 数据层：目标枚举（远端/本地）、单份 SSH 配置（主机、端口、用户、认证方式、隧道端口）、会话（只持有传输对象）
- 传输层：向视图与读取循环暴露 `stdin`、`stdout`、`pty`、`pid`、`isAlive()`、`destroy()`、`awaitExit()`
- 提供者层：`startSession` 返回会话传输；`executeHiddenCommand` 承担不可见执行；`getFileSystemProvider` 支撑文件工具
- 连接管理：会话复用、端口转发、隧道、挂载，按连接 ID 隔离
- 状态机层：把原始字节流切成行，判定提示符、命令边界、交互式提示，推进会话初始化状态
- 界面层：终端画布、命令输入、设置页、主机密钥确认对话框、缺配置引导

## 四、传输抽象契约

这是整个改造的支点：视图、读取循环、退出处理必须读同一份状态，因此不要给远程会话留空对象。

```
interface TerminalTransport {
    val stdin: OutputStream
    val stdout: InputStream
    val pty: Pty?                   // 远端也必须给出实现，见第六节
    val pid: Int?                   // 远端为 null
    fun isAlive(): Boolean
    fun destroy()
    suspend fun awaitExit(): Int?   // 退出码；远端为 null 表示对端直接断开
}
```

本地实现包一个 `Process` 或 PTY 句柄；远程实现包一个 SSH 通道。`TerminalSession` 只持有传输，`stdin`/`stdout`/`pty` 做成转发属性，避免视图与读取循环各拿一份旧引用。

两个容易踩的实现细节：

- 通道的 `InputStream`/`OutputStream` 要在 `connect()` 之前取出来。先取再连，读到的是同一个通道缓冲，不会丢首屏输出
- 退出处理要读退出码，而读退出码是挂起操作，必须放进不可取消的作用域，否则协程一取消，退出码与状态清理会静默丢失

## 五、会话就绪握手（最容易漏的契约）

终端状态机不能靠「等一会儿」判断会话可用，它依赖三段真实信号：

1. `LOGIN_SUCCESSFUL`：登录态确认
2. `TERMINAL_READY`：环境就绪
3. 首个提示符：进入可执行状态 `READY`

`createNewSession` 只在 `READY` 时返回，超时通常设 30 秒。

坑在于：本地沙箱由启动脚本打印这两个标记，远端 SSH 对面是一台普通 sshd，不会有任何标记，于是状态机永远停在初始化态。失败表现极具误导性——命令其实已经写进远端 shell 并执行成功，远端文件真的被创建，但工具每次都报 `Session initialization timeout`；依赖同一路径的 MCP 共享会话同样失败。

两种实现方式，选其一并写进 provider 契约：

- 通道打开后立即向远端 shell 写入 `echo LOGIN_SUCCESSFUL; echo TERMINAL_READY`，远端执行完会重新打印提示符，走完同一状态机
- 或者扩展状态机，让「首次出现提示符」在远端模式下也能推进到 `READY`；这要求状态机知道会话类型，耦合更重

标记行的顺序不敏感，因为每个状态下只关心自己那一个标记；输入回显会把标记文本带回屏幕，同样无影响。选择注入命令时要保证标记文本短到不会被终端折行拆散。

配套要求：远端目标缺少配置时要在进入状态机之前快速失败并弹引导，而不是让用户陪着等满 30 秒超时。

## 六、窗口尺寸链路

PTY 请求必须带尺寸，否则服务端按 80×24 分配；之后所有尺寸变化都要通过 window-change 下发。

- 打开通道：`setPtyType("xterm-256color")`、`setPtySize(cols, rows, 0, 0)`，给出初始 80×24
- 传输层的 `pty` 实现 `setWindowSize(rows, cols)`，内部转发为 `channel.setPtySize(cols, rows, 0, 0)`
- 视图在尺寸变化时计算行列并下发，且要在后台线程调用，避免通道阻塞时拖住主线程
- 尺寸计算必须与渲染视口用同一套基准：要么窗口不随输入法变化（把窗口设为 `ADJUST_NOTHING`，自己减一次输入法高度），要么让外层布局随输入法缩小（画布不再减），两种都自洽，混用就会把行数压到 1
- 缩到可用面积时记得留底线：宿主界面各自占据的高度（顶部栏、会话标签、工具行、输入行）加上软键盘后，画布可能只剩几百像素；此时行数会掉到个位数，极端情况下靠 `coerceAtLeast(1)` 兜成 1 行，远端 `tmux`、`less`、进度条都会失真。这是布局取舍，改法是键盘弹起时收起工具行、缩小字号，或让画布覆盖键盘区域，而不是在行列计算里打补丁

验收方法：把远端会话里跑一个每两秒记录一次 `stty size` 的循环，输出写文件而不打到终端（避免持续重绘），然后改变设备显示尺寸，比对「日志里的 window-change 请求值」和「远端读到的实际值」。两侧一致才算打通。

## 七、主机密钥校验

- 首次连接返回未知主机挑战，由用户确认后写入 `known_hosts`，之后命中即视为可信
- 指纹变化必须与「未知主机」区分：前者是中间人攻击信号，对话框文案与操作都要不同（明确提示风险，只允许删除旧记录后重连，不提供「继续」）
- 存储格式用 OpenSSH `known_hosts`，便于用户导入导出与人工核对
- 指纹按 `SHA256:` 加 base64 去填充的形式展示，与 `ssh-keygen -lf` 输出一致，方便现场比对
- 客户端要显式设置 `StrictHostKeyChecking=yes` 并挂上自己的密钥仓库实现，不要依赖库的默认宽松行为

验证时可用服务端日志交叉确认：客户端拒绝时，服务端会记录 `JSchUnknownHostKeyException: reject HostKey ... [preauth]`，证明是客户端主动拒绝而不是服务端不可达。

## 八、凭据与配置落盘

- 口令、私钥口令、设备侧回连口令统一走平台密钥库加密（Android 用 Keystore 的 AES-GCM），配置文件里只留密文与一个格式标记
- 旧版本明文配置要在读取时就地加密并回写，否则升级后的第一次读取会把明文原样留在磁盘上，加密形同虚设
- 加密不可用时不要吞掉原值：保留旧值并记日志，用户重新输入即可，而不是把手里的唯一凭据丢掉
- 任何设备侧回连口令都必须每次安装随机生成，硬编码或全设备统一的默认口令等于没有口令
- 解密失败按「凭据不可用」处理，交给用户重新输入，不要把一个坏值继续当口令用

## 九、认证方式

两种认证都要支持，并且由用户配置显式决定，不做猜测式尝试：

- 口令：`session.setPassword(plain)`
- 私钥：`jsch.addIdentity(path)`，有口令时 `addIdentity(path, passphrase)`；私钥路径由用户配置，指向应用可读的文件

验收时两侧都要取证据：客户端日志出现会话建立与通道打开，服务端日志出现 `Accepted publickey for <user> ... ssh2: RSA SHA256:<fp>`，指纹要与本地 `ssh-keygen -lf` 一致。

## 十、不可见执行

给 Agent 或工具用的批量执行建议走独立的 exec 通道，不要借用可见会话，否则会把 Agent 的输出混进用户屏幕、把用户的输入混进命令结果。

- 远端：一条命令一个 exec 通道，收集标准输出与标准错误、等待通道关闭、读取退出码
- 本地或长驻通道：用带内标记信封把命令包起来，形如「开始标记 + 命令 ID、PID 标记、结束标记 + 退出码」，读取端按标记切分输出并解析退出码
- 超时必须能真正中止：拿到 PID 后对进程组先 SIGTERM 再 SIGKILL，不能只停止读取
- 结果里要同时带输出、退出码与状态枚举（超时、进程提前退出、缺少标记、退出码非法），调用方才能区分「命令失败」与「通道坏了」

## 十一、端口转发与隧道

两个方向解决两个不同问题，名字要起清楚，避免混用：

| 方向 | 用途 | 实现 |
| --- | --- | --- |
| 本地转发 | 把远端服务映射到设备回环，供本机组件访问 | `setPortForwardingL(localPort, "localhost", remotePort)` |
| 反向隧道 | 让远端能回连设备，用于把设备存储挂给远端 | `setPortForwardingR(remotePort, "localhost", localSshPort)` |

要点：

- 反向隧道需要在远端 sshd 上允许转发；要让远端之外的地址也能连，还要开 `GatewayPorts`
- 端口被占用、服务端拒绝转发都会让建立失败，应按能力开关而不是静默忽略
- 与反向隧道配套的设备侧 sshd 只提供 SFTP 子系统是合理取舍：远程文件挂载只需要 SFTP，不需要给远端一个 shell
- 远端挂载通常依赖 `sshfs`，缺失时应用要把「远端缺依赖」这一事实回显给用户，而不是只留一句失败

验收方法：本地转发方向在远端起一个监听并回一句话，设备侧连本地端口，两侧都能看到对方的载荷；反向隧道方向用 `sftp -P <remotePort> <user>@127.0.0.1` 列出设备共享目录的实际内容。

## 十二、设备侧内嵌 sshd

反向隧道要让远端访问设备，设备侧就得有一个 sshd。在应用进程内启动一个纯 Java 的 sshd 实现是成本最低的做法：

- 端口取配置里的设备侧端口，认证直接比对配置里的用户名与口令
- 用虚拟文件系统把根目录限制在共享存储，避免把应用私有目录暴露出去
- 只挂 SFTP 子系统即可；不提供 shell 与 exec 通道是安全默认值
- 该 sshd 的失败要当作配置问题提示用户，而不是让反向隧道静默变成「连得上但用不了」

远端用 `ssh` 直接连这个 sshd 会得到 `exec request failed on channel 0` 或 `shell request failed on channel 0`，这是预期行为，不是隧道没通。

## 十三、失败模式对照表

移植时按症状直接查这一栏，可以省掉大部分返工。

| 症状 | 真实根因 | 确认方法 |
| --- | --- | --- |
| 工具报会话初始化超时，但远端文件确实被创建 | 缺少就绪握手标记 | 看状态机日志有没有出现两个标记与首个提示符 |
| 提示符出现但全屏程序只剩几行，极端情况下变成 1 行 | 两种可能：尺寸基准被混用（输入法高度被减了两次），或宿主界面加软键盘把画布挤到几百像素 | 远端循环记录 `stty size`，与 window-change 请求值比对；两者一致就说明算术没错，问题在布局 |
| 所有 HTTPS 请求立刻失败 | 容器或系统缺 CA 证书包 | 用详细模式跑一次请求，看到证书文件缺失的错误号 |
| 批处理式文件传输报认证被拒，交互命令却正常 | 批处理模式隐式禁用了口令提示 | 去掉批处理开关，改用标准输入喂命令 |
| 远端 `ssh` 连设备得到 exec/shell 失败 | 设备侧 sshd 只挂 SFTP 子系统 | 换成 `sftp` 客户端复测 |
| 移动端界面无响应、主线程卡在绘制 | 软件渲染下画布持续重绘耗尽渲染线程 | 换成宿主 GPU 渲染复测 |
| 与较新的 OpenSSH 服务端握手失败 | 客户端库过旧，签名算法被服务端默认关闭 | 换用维护中的分支并确认算法协商 |
| 连不上但日志只有「连接中」 | 连接超时很长，早期失败被超时掩盖 | 缩短连接超时并在失败分支打日志 |

## 十四、验证脚手架

这套东西值得做一次固化，后续每个版本都能重跑：

- 一台可复现的测试主机：镜像里预装 sshd、客户端、`tmux`、`curl`、`pandoc`、`netcat`、`sshpass` 与 CA 证书包；创建固定测试账号，口令写明是测试口令
- 一套密钥材料：测试用密钥对 + 写入 `authorized_keys` 的脚本 + 一条本机自测命令，先证明服务端认可这把钥匙，再拿它去验客户端
- 一组断言脚本：就绪握手、窗口尺寸、私钥认证、正反两个方向的隧道、SFTP 回连、文件落到远端
- 一条原则：每个结论都要在「客户端日志」与「服务端日志或服务端文件系统」两侧各取一份证据，单侧证据很容易把客户端 bug 当成服务端行为

## 十五、移植清单

按职责搬，不要按文件搬；下面每一条都是一个必须满足的不变量。

1. 会话统一由状态机管理，任何执行路径都不绕过它就绪判断
2. 传输对象同时提供输入、输出、PTY 与退出等待，远程不留空实现
3. 就绪由真实信号驱动，不用固定睡眠猜
4. 主机密钥永不跳过校验，未知与变更分开处理
5. 凭据落盘一律加密，且能就地迁移旧明文
6. 远端连不上就报错并引导，不静默回落本地
7. 尺寸变化必须下发 window-change，且与渲染视口口径一致
8. 命令结果必须带退出码与可区分的失败状态
9. 隧道与转发按开关建立，失败要可见
10. 设备侧回连口令每次安装随机

配套依赖只需要一个纯 Java 的 SSH 库和平台密钥库；Android 侧另外需要网络权限，以及用于展示确认对话框的悬浮窗权限，否则工具权限确认会因为弹不出窗口而超时失败。
